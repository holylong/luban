# Codex 额度消耗排查（2026-10-14）

此次排查发现三处会额外重发上下文或启动总结请求的问题，以及一处用量重复计数，
已在 1.16.96 修复。
这些问题足以解释部分额外消耗，但不能据此计算与原生 Codex 的额度消耗倍数。

## 本机记录

扫描本机最近 150 个 Codex JSONL 会话文件，以 luban 的转接提示识别出 26 个 CLI
线程、83 次 luban 请求。仅提取用量和调用结构，未导出任务正文或登录凭据。
有 token 记录的线程合计如下（这是采样范围内的累计处理量）：

| 指标 | Token |
| --- | ---: |
| 输入 | 8,175,592 |
| 其中缓存输入 | 5,646,464 |
| 非缓存输入 | 2,529,128 |
| 输出 | 65,033 |
| 其中推理输出 | 4,334 |

缓存输入包含在输入总数中，推理输出包含在输出总数中，不能重复相加。
记录中的推理强度均为 medium；这些线程未发现 Codex 原生工具调用。
多个新线程首轮带有几十至上百条历史消息，并出现缓存输入为零的记录。
例如，一个线程首轮包含 174 条消息，桥接提示最大为 574,430 字符；另一个线程
经过 8 轮请求累计处理 1,241,300 个输入 token，其中 1,035,520 个缓存输入。

## 修复

1. **跨用户轮次续接失效。** 原实现用消息数组对象作线程索引，TUI 每次发送消息都
   创建新数组，导致已有线程无法匹配。主任务现在使用运行器内稳定的会话标识；
   同一会话的复制数组继续精确续接，辅助总结请求仍隔离。
2. **计划更新引起全量重发。** 计划插入在历史前部，更新又修改已有系统消息，打破
   旧实现的历史前缀匹配。计划和验证状态现在单独跟踪，发生变化时显式发送当前
   权威状态，不会因此新建线程。实际历史修改、规则变化和压缩仍使旧线程失效。
3. **未发送的输出预算触发压缩。** Codex CLI 接管输出长度，luban 未向它发送
   `max_tokens`，却把默认 64,000 当成输出预留，从而压缩本来可以保留的历史。
   Codex 的本地输入预算现在按 `context_window`、`context_reserve` 和工具清单计算。
4. **累计 token 重复计入显示统计。** CLI 在续接后返回线程累计用量，原实现却把
   累计值当成当前请求用量。一个保存的会话将首轮 19,314 输入 token 与第二轮的
   累计 39,219 相加，显示 58,533；第二轮的实际新增输入只有 19,905。
   现在缓存累计值并逐轮差分，输入、缓存、输出及推理统计都按新增量记录。
   这个问题夸大 luban 的显示统计，不会直接造成账号多扣额度。

回归测试用记录请求参数和标准输入的本地 CLI 替身复现原问题，并验证复制会话、
计划及验证更新继续使用 `exec resume`，不重发原任务或完整工具清单；也验证会话
隔离、失败后线程失效，以及可容纳的历史不会产生额外总结请求。

## 范围与限制

Codex 的自动会话标题请求和 luban 层超时重放原本已关闭，此次保持这些行为。
未更改用户选择的模型或推理强度，也没有为了排查发起新的真实模型请求。
重新启动 luban 或更换运行器后，CLI 线程关联仍需重建；JSON 工具转接、工具结果和
两层指令仍有额外上下文开销。此实现目前不能保证与原生 Codex 的消耗完全相同。

本次没有在同一模型、推理强度、任务、历史和时间窗口下取得原生 Codex 的对照
数据，也没有测量修复后的订阅额度下降比例。OpenAI 的[官方额度说明](https://learn.chatgpt.com/docs/pricing)
说明上下文、模型、推理、工具和缓存都会影响消耗；不能直接把上述 token 总数或
输入字符减少比例换算为订阅额度节省比例。
