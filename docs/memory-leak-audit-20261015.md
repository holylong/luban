# 长时间运行后的堆内存耗尽（1.16.100）

用户报告 Windows 和 Linux 均出现 `Ineffective mark-compacts near heap limit`。
日志中进程已运行约 13 小时 40 分钟，Mark-Compact 后仍保留约 4019 MB。
这说明 V8 堆接近上限且无法回收足够对象；仅凭日志无法识别具体保留路径。

## 已确认的泄漏

当前锁定的 Ink 6.8.0 在 `measure-text.js` 和 `wrap-text.js` 中分别使用
模块级 Map 和对象缓存完整文字，没有淘汰或容量限制。流式回答、计时状态和输入
每次变化都会留下新的缓存，即使文本已离开屏幕，也会一直保留到进程退出。
该行为与操作系统无关。上游也有[同一问题及修复讨论](https://github.com/vadimdemedes/ink/pull/987)。

直接调用本机实际安装的文字测量与截断函数，每批输入 5000 条随机生成的
2048 字符文字；每批后主动执行 GC，记录 `heapUsed`：

| 不同文字数量 | 修复前（MiB） | 修复后（MiB，约） |
| --- | ---: | ---: |
| 0 | 4.7 | 5.4 |
| 5000 | 26.5 | 9.9 |
| 10000 | 47.5 | 9.9 |
| 15000 | 68.4 | 9.9 |
| 20000 | 89.4 | 9.9 |
| 40000 | 未运行 | 9.9 |

这些是隔离渲染缓存复现进程的数据，不是整个 luban 的内存用量。
修复前主动 GC 后仍线性上涨，确认不是单纯临时分配引起的内存峰值。

## 修复与安装路径

保留现有 Ink 版本和终端输入行为，在安装/构建阶段回补缓存限制：每个缓存
最多保留 2048 项、估算 4 MiB 的内容，读取时更新最近使用顺序，超限淘汰旧项，
单项过大则不缓存。复制字符串以防小切片间接保留整个巨大原始字符串；UTF-16
复制保留中文、表情及孤立代理字符。换行缓存键改为明确的参数元组以避免碰撞。
这些预算约束缓存内容，不代表整个 Node.js 进程的内存上限。

- npm 安装执行 `scripts/patch-ink.mjs`（postinstall）。
- `npm run build` 同样执行补丁，覆盖源码安装时跳过生命周期脚本的情况。
- Windows/Linux CLI/Desktop 打包器在 `npm ci --omit=dev --ignore-scripts` 后显式
  修补打包目录中的依赖，包内同时保留 postinstall 所需脚本。
- 补丁可重复运行；Ink 版本或预期源码变化会明确报错，要求审查兼容性。
- 文件编辑记录、会话保存及恢复、计划侧栏均不受缓存淘汰影响。

原有安装需更新依赖和构建产物，已有便携包或安装包需要重新打包。npm 安装若使用
`--ignore-scripts` 且不运行完整构建，需手动执行 `node scripts/patch-ink.mjs`。
单纯提高堆上限不能解决缓存持续增长。

## 验证与边界

`node --expose-gc --max-old-space-size=128 scripts/ink-memory-smoke.mjs` 验证真实
Ink 模块处理 40000 条不同文字后内存保持稳定，并覆盖小切片保留大字符串的问题。
测试还覆盖缓存淘汰、中文/表情、换行/截断结果、重复安装和不兼容依赖的报错。
已有 Windows 重绘和交互回归测试通过；已从 npm 归档执行全新生产依赖安装，
验证 postinstall 和跳过脚本后的显式修补两条路径。

当前验证在 Linux 上执行，未在原生 Windows 上做长时间运行测试。
没有用户崩溃时的堆快照，因此不能断言此次崩溃只有这一个原因。如果修复后仍增长，
应区分主进程退出与工具子进程（例如构建命令）耗尽内存，再进一步取样定位。
