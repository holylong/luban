## 思考流输出闪烁排查（v1.16.104）

### 原因与复现

旧的 `windowsOutput` 只在 `win32` 的交互终端启用行更新。Linux 仍直接接收 Ink 标准渲染器的“擦除上一帧，再写入新帧”序列。即使界面高度固定、没有 `ESC[2J` 全屏清除，每次思考更新仍会产生几十条 `ESC[2K` 行擦除。不能原子呈现同步更新的终端可能显示擦除与重画之间的空白。

在真实 App 树上模拟模型逐段发送思考，接入与 CLI 相同的输出代理后，旧代码的 Linux 路径稳定触发行擦除测试失败，Windows 路径通过。旧的布局测试只检查高度、光标漂移和全屏清除，未检查持续思考过程中的整帧行擦除。

### 修改与边界

- 将代理改为 `terminalOutput`，所有交互 TTY 都使用固定高度帧的行更新，无需更改 Ink 的标准渲染器和尾随换行约定。
- 保持吉祥物背景先合成、再比较终端行的顺序；保留未变化的历史、计划和背景行。
- 改变尺寸、外部输出、未知控制序列、二进制写入时回退并重新建立基准；屏幕阅读器和重定向输出不使用代理。
- 不启用 Ink 的增量渲染器，避免已有的光标逐行漂移问题。

### 验证

回归测试使用模拟 TTY 和真实 Ink 输出，覆盖 60、100、160 列，连续中文、换行、长思考行、emoji，以及吉祥物输出链。稳定流式阶段要求没有整帧行擦除或全屏清除、没有重发已有历史；现有测试继续验证输入行定位及窗口缩放后的恢复。

这验证了输出序列和布局；实际终端的视觉表现仍取决于终端实现。首次绘制和窗口缩放可能仍走完整重画路径。

## 界面排版复用（1.16.101）

流式回答更新时，终端原本会把历史消息与当前回答合成新数组，再对全部内容解析
Markdown、生成执行行并换行。网页和桌面端共用的 Transcript 则会收到事件重放后
新建的历史条目，重复生成未变化条目的 React 子树、Markdown 和语法高亮节点。

### Pretext 评估

检查父目录 pretext 的本地提交 `0a27bbe0`、公开 API 和 Markdown 聊天示例。
[Pretext](https://github.com/chenglou/pretext) 把文字分段、Canvas 字宽测量放在
`prepare()`，然后复用测量结果计算布局。它不负责 React 协调或 DOM 差异更新。

在 Node.js 22.19.0 直接调用本地源码编译后的 `prepare()`，报错
`Text measurement requires OffscreenCanvas or a DOM canvas context.`。
终端需要字符列宽，Canvas 的像素字宽也不能代替它。网页/桌面端可以使用该库，
但当前主要重复的是 React/Markdown 计算，并没有逐条测量 DOM 高度的流程；单独
加入 Canvas 测量不会自动解决这个问题。因此本次采用预处理、复用未变结果的
思路，没有新增 Pretext 依赖，也未修改父目录的 Pretext 项目。

### 变化

- 终端将历史记录和当前输出分开。只有历史内容、详情模式、终端宽度或活动记录
  变化时才重建历史排版；流式回答仍完整解析，正确处理后续闭合的代码围栏和强调。
- 每个挂载视图只保留一份当前历史排版；切换会话和宽度时替换，不积累历次缓存。
- 历史行对象保持稳定，行组件可复用。主题修订号显式触发重绘，选区变化正常更新。
- 网页和桌面共用的记录组件按可见字段判断变化。事件重放生成新对象时，未变化的
  历史内容跳过重新渲染；工具状态、命令参数、输出、耗时和编辑记录变化正常刷新。
- Markdown 和代码行组件单独复用，保留 DOM、卡片展开状态、文本选择和浏览器查找。

Ink 仍会布局当前视口并输出终端帧；网页仍会布局实际改变的 DOM。本次没有替换
渲染器，也没有把长历史从 DOM 中卸载。文件修改记录和会话持久化均保持完整。

覆盖当前输出变化时复用历史、Markdown 后续语法闭合、宽度/会话失效、恢复的编辑
记录、工具元数据更新。真实浏览器检查工具执行中到完成、折叠状态保留、已展开
编辑差异更新、HTML 转义和历史 DOM 保持。原有主题切换、Mesh、本地对话、终端
重绘、鼠标、滚动和内存限制回归继续通过。

## 长时间运行后的堆内存耗尽（1.16.100）

用户报告 Windows 和 Linux 均出现 `Ineffective mark-compacts near heap limit`。
日志中进程已运行约 13 小时 40 分钟，Mark-Compact 后仍保留约 4019 MB。
这说明 V8 堆接近上限且无法回收足够对象；仅凭日志无法识别具体保留路径。

### 已确认的泄漏

当前锁定的 Ink 6.8.0 在 `measure-text.js` 和 `wrap-text.js` 中分别使用
模块级 Map 和对象缓存完整文字，没有淘汰或容量限制。流式回答、计时状态和输入
每次变化都会留下新的缓存，即使文本已离开屏幕，也会一直保留到进程退出。
该行为与操作系统无关。上游也有[同一问题及修复讨论](https://github.com/vadimdemedes/ink/pull/987)。

直接调用本机实际安装的文字测量与截断函数，每批输入 5000 条随机生成的
2048 字符文字；每批后主动执行 GC，记录 `heapUsed`：

| 不同文字数量 | 修复前（MiB） | 修复后（MiB，约） |
| --- | ---: | ---: |
| 0 | 4.7 | 5.4 |
| 5000 | 26.5 | 9.9 |
| 10000 | 47.5 | 9.9 |
| 15000 | 68.4 | 9.9 |
| 20000 | 89.4 | 9.9 |
| 40000 | 未运行 | 9.9 |

这些是隔离渲染缓存复现进程的数据，不是整个 luban 的内存用量。
修复前主动 GC 后仍线性上涨，确认不是单纯临时分配引起的内存峰值。

### 修复与安装路径

保留现有 Ink 版本和终端输入行为，在安装/构建阶段回补缓存限制：每个缓存
最多保留 2048 项、估算 4 MiB 的内容，读取时更新最近使用顺序，超限淘汰旧项，
单项过大则不缓存。复制字符串以防小切片间接保留整个巨大原始字符串；UTF-16
复制保留中文、表情及孤立代理字符。换行缓存键改为明确的参数元组以避免碰撞。
这些预算约束缓存内容，不代表整个 Node.js 进程的内存上限。

- npm 安装执行 `scripts/patch-ink.mjs`（postinstall）。
- `npm run build` 同样执行补丁，覆盖源码安装时跳过生命周期脚本的情况。
- Windows/Linux CLI/Desktop 打包器在 `npm ci --omit=dev --ignore-scripts` 后显式
  修补打包目录中的依赖，包内同时保留 postinstall 所需脚本。
- 补丁可重复运行；Ink 版本或预期源码变化会明确报错，要求审查兼容性。
- 文件编辑记录、会话保存及恢复、计划侧栏均不受缓存淘汰影响。

原有安装需更新依赖和构建产物，已有便携包或安装包需要重新打包。npm 安装若使用
`--ignore-scripts` 且不运行完整构建，需手动执行 `node scripts/patch-ink.mjs`。
单纯提高堆上限不能解决缓存持续增长。

### 验证与边界

`node --expose-gc --max-old-space-size=128 scripts/ink-memory-smoke.mjs` 验证真实
Ink 模块处理 40000 条不同文字后内存保持稳定，并覆盖小切片保留大字符串的问题。
测试还覆盖缓存淘汰、中文/表情、换行/截断结果、重复安装和不兼容依赖的报错。
已有 Windows 重绘和交互回归测试通过；已从 npm 归档执行全新生产依赖安装，
验证 postinstall 和跳过脚本后的显式修补两条路径。

当前验证在 Linux 上执行，未在原生 Windows 上做长时间运行测试。
没有用户崩溃时的堆快照，因此不能断言此次崩溃只有这一个原因。如果修复后仍增长，
应区分主进程退出与工具子进程（例如构建命令）耗尽内存，再进一步取样定位。

## Codex 额度消耗排查（2026-10-14）

此次排查发现三处会额外重发上下文或启动总结请求的问题，以及一处用量重复计数，
已在 1.16.96 修复。
这些问题足以解释部分额外消耗，但不能据此计算与原生 Codex 的额度消耗倍数。

### 本机记录

扫描本机最近 150 个 Codex JSONL 会话文件，以 luban 的转接提示识别出 26 个 CLI
线程、83 次 luban 请求。仅提取用量和调用结构，未导出任务正文或登录凭据。
有 token 记录的线程合计如下（这是采样范围内的累计处理量）：

| 指标 | Token |
| --- | ---: |
| 输入 | 8,175,592 |
| 其中缓存输入 | 5,646,464 |
| 非缓存输入 | 2,529,128 |
| 输出 | 65,033 |
| 其中推理输出 | 4,334 |

缓存输入包含在输入总数中，推理输出包含在输出总数中，不能重复相加。
记录中的推理强度均为 medium；这些线程未发现 Codex 原生工具调用。
多个新线程首轮带有几十至上百条历史消息，并出现缓存输入为零的记录。
例如，一个线程首轮包含 174 条消息，桥接提示最大为 574,430 字符；另一个线程
经过 8 轮请求累计处理 1,241,300 个输入 token，其中 1,035,520 个缓存输入。

### 修复

1. **跨用户轮次续接失效。** 原实现用消息数组对象作线程索引，TUI 每次发送消息都
   创建新数组，导致已有线程无法匹配。主任务现在使用运行器内稳定的会话标识；
   同一会话的复制数组继续精确续接，辅助总结请求仍隔离。
2. **计划更新引起全量重发。** 计划插入在历史前部，更新又修改已有系统消息，打破
   旧实现的历史前缀匹配。计划和验证状态现在单独跟踪，发生变化时显式发送当前
   权威状态，不会因此新建线程。实际历史修改、规则变化和压缩仍使旧线程失效。
3. **未发送的输出预算触发压缩。** Codex CLI 接管输出长度，luban 未向它发送
   `max_tokens`，却把默认 64,000 当成输出预留，从而压缩本来可以保留的历史。
   Codex 的本地输入预算现在按 `context_window`、`context_reserve` 和工具清单计算。
4. **累计 token 重复计入显示统计。** CLI 在续接后返回线程累计用量，原实现却把
   累计值当成当前请求用量。一个保存的会话将首轮 19,314 输入 token 与第二轮的
   累计 39,219 相加，显示 58,533；第二轮的实际新增输入只有 19,905。
   现在缓存累计值并逐轮差分，输入、缓存、输出及推理统计都按新增量记录。
   这个问题夸大 luban 的显示统计，不会直接造成账号多扣额度。

回归测试用记录请求参数和标准输入的本地 CLI 替身复现原问题，并验证复制会话、
计划及验证更新继续使用 `exec resume`，不重发原任务或完整工具清单；也验证会话
隔离、失败后线程失效，以及可容纳的历史不会产生额外总结请求。

### 范围与限制

Codex 的自动会话标题请求和 luban 层超时重放原本已关闭，此次保持这些行为。
未更改用户选择的模型或推理强度，也没有为了排查发起新的真实模型请求。
重新启动 luban 或更换运行器后，CLI 线程关联仍需重建；JSON 工具转接、工具结果和
两层指令仍有额外上下文开销。此实现目前不能保证与原生 Codex 的消耗完全相同。

本次没有在同一模型、推理强度、任务、历史和时间窗口下取得原生 Codex 的对照
数据，也没有测量修复后的订阅额度下降比例。OpenAI 的[官方额度说明](https://learn.chatgpt.com/docs/pricing)
说明上下文、模型、推理、工具和缓存都会影响消耗；不能直接把上述 token 总数或
输入字符减少比例换算为订阅额度节省比例。

## 运行性能（1.16.83）

本次优化减少运行时引起的额外模型请求和重复检查，不改变模型服务本身的响应速度。

- 上下文达到可用输入预算的 80% 才压缩，目标为 60%，给后续调用留空间。`max_history_messages` 限制压缩后的保留量，不再单凭消息数触发压缩。仅裁剪工具输出时不请求语义摘要。
- Anthropic 和 Responses 支持逐请求的输出上限、连接超时、流空闲超时和重试参数；Codex 支持逐请求调整推理强度。自动推理只根据最近一批工具错误恢复，错误解决后回到快速执行。
- `read_files` 一次接收最多 8 个文件，每个文件仍经过路径权限和目录指令检查，保留独立执行记录。独立的 `bash` 调用可设 `independent: true`；有共享写入或先后依赖的命令继续顺序执行。并发上限为 4，完成一个就反馈一个，历史结果仍按原调用顺序保存。
- TypeScript 服务按项目复用，最多缓存 4 个项目；文件、依赖、配置和源文件列表变化会刷新分析。编辑工具直接返回 TypeScript/JavaScript 或已配置 LSP 的诊断。诊断不可用时仍保留修改记录，并提示使用项目检查。单文件诊断不能替代项目构建和测试。
- TUI 和命令行展示模型耗时、工具累计耗时、审批等待和压缩次数。会话的 `performance.requests` 保存逐请求耗时及首次文本/推理输出时间。无文本或推理输出时不填首次输出时间；模型耗时包含适配器内部重试，工具累计耗时在并发时可能超过实际墙钟时间。

网关可在模型或提供商配置中设置 `thinking_control`，覆盖原生推理参数的自动识别：`qwen`、`thinking`、`reasoning-effort`、`adaptive`、`budget`、`none`。`none` 用于不支持这些参数的网关。低推理强度不等于完全关闭推理。

### 本地测量

相同工作区的 `src/core/agent.ts`，比较修改前构建与修改后构建的进程内语言服务，每个版本连续查询三次 symbols、两次 diagnostics：

| 查询 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 第二次 symbols | 644 ms | 16 ms |
| 第三次 symbols | 598 ms | 12 ms |
| 第二次 diagnostics | 910 ms | 8 ms |

所有查询结果数量相同：symbols 为 615，diagnostics 为 0。首次查询仍需建立项目；这组数值主要反映复用后的改善，不能外推为完整任务加速比例。`code_intel_worker: true` 仍使用一次性隔离进程，这组缓存收益适用于默认的进程内模式。

在可用输入预算 229,376、保留消息上限 60 的 50 轮小工具结果模拟中，原策略压缩 21 次，新策略为 0 次；最终估算 token 为 14,167，仍低于触发阈值。

可重新测量当前版本（耗时随机器和项目变化）：

```sh
npm run build
node scripts/benchmark-runtime.mjs
```

基准脚本不调用模型服务，不改写工作区。上述测试没有测量真实模型任务的端到端速度。
