# 运行性能（1.16.83）

本次优化减少运行时引起的额外模型请求和重复检查，不改变模型服务本身的响应速度。

- 上下文达到可用输入预算的 80% 才压缩，目标为 60%，给后续调用留空间。`max_history_messages` 限制压缩后的保留量，不再单凭消息数触发压缩。仅裁剪工具输出时不请求语义摘要。
- Anthropic 和 Responses 支持逐请求的输出上限、连接超时、流空闲超时和重试参数；Codex 支持逐请求调整推理强度。自动推理只根据最近一批工具错误恢复，错误解决后回到快速执行。
- `read_files` 一次接收最多 8 个文件，每个文件仍经过路径权限和目录指令检查，保留独立执行记录。独立的 `bash` 调用可设 `independent: true`；有共享写入或先后依赖的命令继续顺序执行。并发上限为 4，完成一个就反馈一个，历史结果仍按原调用顺序保存。
- TypeScript 服务按项目复用，最多缓存 4 个项目；文件、依赖、配置和源文件列表变化会刷新分析。编辑工具直接返回 TypeScript/JavaScript 或已配置 LSP 的诊断。诊断不可用时仍保留修改记录，并提示使用项目检查。单文件诊断不能替代项目构建和测试。
- TUI 和命令行展示模型耗时、工具累计耗时、审批等待和压缩次数。会话的 `performance.requests` 保存逐请求耗时及首次文本/推理输出时间。无文本或推理输出时不填首次输出时间；模型耗时包含适配器内部重试，工具累计耗时在并发时可能超过实际墙钟时间。

网关可在模型或提供商配置中设置 `thinking_control`，覆盖原生推理参数的自动识别：`qwen`、`thinking`、`reasoning-effort`、`adaptive`、`budget`、`none`。`none` 用于不支持这些参数的网关。低推理强度不等于完全关闭推理。

## 本地测量

相同工作区的 `src/core/agent.ts`，比较修改前构建与修改后构建的进程内语言服务，每个版本连续查询三次 symbols、两次 diagnostics：

| 查询 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 第二次 symbols | 644 ms | 16 ms |
| 第三次 symbols | 598 ms | 12 ms |
| 第二次 diagnostics | 910 ms | 8 ms |

所有查询结果数量相同：symbols 为 615，diagnostics 为 0。首次查询仍需建立项目；这组数值主要反映复用后的改善，不能外推为完整任务加速比例。`code_intel_worker: true` 仍使用一次性隔离进程，这组缓存收益适用于默认的进程内模式。

在可用输入预算 229,376、保留消息上限 60 的 50 轮小工具结果模拟中，原策略压缩 21 次，新策略为 0 次；最终估算 token 为 14,167，仍低于触发阈值。

可重新测量当前版本（耗时随机器和项目变化）：

```sh
npm run build
node scripts/benchmark-runtime.mjs
```

基准脚本不调用模型服务，不改写工作区。上述测试没有测量真实模型任务的端到端速度。
